# claude-code

## Purpose
Installs the Claude Code CLI (Nix package + Obsidian MCP cert trust) and, independently, symlinks the shared `~/.claude-config` git repo (skills/agents/commands/CLAUDE.md/engineering-principles.md) into `~/.claude/` so all hosts share one config. Enable via `hwc.home.apps.claude-code.enable`; `shareConfig.enable` can be turned on standalone (e.g. hwc-server, which runs claude from npm).

## Boundaries
- ✅ `pkgs.claude-code`, a `claimcheck` wrapper with its `jsonschema` Python runtime, `NODE_EXTRA_CA_CERTS` pointing at the Obsidian Local REST API cert, `mkOutOfStoreSymlink` links for `shareConfig.items`, optional `claude-config-pull` user service+timer (ff-only pull, default 15min), append-only self-heal of the gate-hook entries into `~/.claude/settings.json` at activation (`shareConfig.wireGateHooks`).
- ❌ Does not manage the claude-config repo contents or clone it; does not touch host-local `~/.claude/{plans,docs,memory}`; never auto-commits/pushes the config repo; never edits or removes existing settings.json entries (heal is append-only — Claude Code stays the file's primary writer).

## Structure
- `index.nix` — options (`enable`, `shareConfig.{enable,repoPath,items,autoPull,wireGateHooks}`), Claude package + cert var, claimcheck runtime wrapper, symlink generation, auto-pull timer, settings.json gate-hook heal activation (fourteen entries), assertions.

- 2026-08-25: `memory-staleness.sh` wired on **SessionStart**, the first read-side memory guard. `memory-lint.sh` validates a memory when it is WRITTEN, but a memory does not go wrong at write time — it goes wrong afterwards, when the world moves and the file does not. Measured on the DataX store that day: 29 of 32 commit SHAs cited across 45 memories had since reached `upstream/prod`, so three files still told the reader that work was merged-but-not-deployed, and one named a prod SHA 60+ commits behind. A stale "deploy owed" reads to the next session as an instruction to skip owed work, which is worse than no memory at all. The hook FETCHES `upstream` (rate-limited, 15 min default, 12 s timeout) and tests every cited SHA against `upstream/prod`, falling back to `upstream/main` only when no prod branch exists; it prints only what git refutes and is silent otherwise. Three deliberate properties: it reads `upstream/*` and never `origin/*`, and a repo with no upstream remote produces no claim at all, because a fork's idea of prod is the fork's idea; a "deploy owed" refutation stays sound against a stale ref (the branch only moves forward) while a "deployed" refutation is suppressed unless the fetch succeeded; and every path derives from `$HOME` and the session cwd, so hwc-laptop and hwc-server behave identically. Self-test: `hooks/memory-staleness.selftest.sh`, 12 checks against the real repository and the real upstream ref — no fake git, per the verify-against-real-systems standing instruction.
- 2026-08-22: three entries added to the settings.json heal, closing the standing-instruction gap. A rule that binds every response has no triggering task, so the memory index's pointer is never opened — measured, 42 of 53 sessions since the rule was written never named its file, and four consecutive responses ignored it. `standing-instructions.sh inject` (UserPromptSubmit) puts the rule TEXT in the turn; `standing-instructions.sh sync` (UserPromptSubmit) regenerates the generated block in `~/.claude-config/CLAUDE.md`, which is the only surface a SUBAGENT loads — sync alone cannot reach the session already running, which is why both are wired. `ste100-guard.sh` is wired on **Stop and SubagentStop**; SubagentStop is the reason this reaches a subagent at all, and it is a real event in Claude Code 2.1.240 (verified against the binary's string table, not assumed). It asks the memory whether the rule is live, so unmarking the memory silences it without touching this file. Measured with guard-replay over 30 transcripts: 99 blocks / 26 sessions, an upper bound rather than a steady rate (the corpus is a world where the agent never adapted).
